# Планирование StudyFlow

## Иерархия

```text
Обучение продуктам (Epic)
└── Осваиваем дашборды (Feature)
    ├── Просмотреть новые учебники (PBI)
    │   ├── Страница последних учебников (Task, Development, 8 ч)
    │   └── Оптимизация запроса (Task, Design, 3 ч)
    ├── Недавно просмотренные учебники (PBI)
    └── Запрос новых материалов (PBI)
```

Спринты: Sprint 1 — 02–15.11.2026; Sprint 2 — 16.11–02.12.2026; Sprint 3 — 03–13.12.2026; Sprint 4 — 14–25.12.2026. На дату начала работы 24.11.2026 текущий спринт — Sprint 2.

## Ёмкость

В Sprint 2 тринадцать рабочих дней. Пять дней отпуска 23–27 ноября исключаются. При доступности 1 ч в день остаётся 8 ч. Первоначальные оценки 5 + 3 = 8 ч соответствуют ёмкости. После уточнения страницы до 8 ч план составляет 8 + 3 = 11 ч; перегрузка равна 3 ч. По условию практики 3 задача остаётся в текущем спринте, чтобы показать конфликт ресурсов.

### Автоматический расчёт из Projects

Исходные данные находятся в самом [GitHub Project](https://github.com/users/IlyaKlinduhov/projects/1/views/3). Строка `[Capacity]` задаёт доступность одного исполнителя в одной итерации. Используются настоящие поля Assignees и «Итерация», число «Часов в день» и текст «Отпуск» с датами в формате `2026-11-23..2026-11-27` (несколько дат или диапазонов через запятую).

Скрипт `project_capacity.py` получает даты и продолжительность итерации через GraphQL, исключает субботы, воскресенья и отпуск. Он суммирует «Осталось, ч» открытых неархивных карточек уровня Task того же исполнителя и итерации; родительские PBI/Feature/Epic и Done исключены. Пустая оценка, отрицательные числа, несколько исполнителей одной задачи и дубли строк ёмкости дают ошибку, а устаревшие числовые итоги очищаются.

Результаты записываются прямо в поля строки `[Capacity]`: «Доступно, ч», «Запланировано, ч», «Перегрузка, ч» и «Расчёт загрузки» с временем UTC и ссылкой на запуск. Перегрузка = max(0, план − доступность).

[Workflow Project capacity](https://github.com/IlyaKlinduhov/software-engineering-practices/actions/workflows/project-capacity.yml) запускается по расписанию каждые 5 минут, при изменении исполнителя/закрытии Issue и вручную через Run workflow. Изменения пользовательских полей персонального Project обрабатываются следующим запуском по расписанию; это не мгновенная реакция, GitHub может задерживать расписание. Отчёт JSON сохраняется артефактом, таблица результатов — в Summary запуска. Компьютер пользователя для этого не нужен.

На время ожидания первого нативного `schedule` подключён [резервный таймер Windows](tools/README.md). Он автоматически запускает тот же облачный workflow каждые пять минут и удаляет собственное задание после первого успешного `schedule` GitHub. Пока используется резервный таймер, компьютер должен быть включён, а пользователь — войти в Windows. Значения в Projects всё равно вычисляет GitHub Actions. Ручного запуска кода при изменении планирования не требуется.

Для работы нужен Actions secret `PROJECTS_TOKEN` с правом `project` (classic PAT). Обычный `GITHUB_TOKEN` репозитория не предоставляет доступ к пользовательскому Project. Токен не хранится в исходниках. При истечении токена workflow завершится ошибкой; дату последнего успешного пересчёта видно в поле «Расчёт загрузки».

`python -m unittest -v` проверяет расчёт и обработку ошибочных данных. `python build.py` собирает каталог; его `dist/capacity.json` является статичным примером и помечен `source: static_example_backlog_json`, а не источником живой загрузки.

## Правила Kanban

| Статус | Критерий перехода |
| --- | --- |
| Backlog | Идея зарегистрирована |
| Approved | Описание и критерии приёмки согласованы |
| Committed | Назначены исполнитель, спринт и оценка |
| QA Doing | Начата проверка, WIP не более 1 |
| QA Done | Тесты и критерии приёмки пройдены |
| Done | Результат принят, Issue закрыт |

Срочная дорожка «Ускорение» используется для недавно просмотренных материалов. Labels `данные`, `ux/ui`, `development` показывают данные, интерфейс и разработку. Поле Ticket ID связывает PBI с внешним обозначением SF-PBI-003/006/007.
